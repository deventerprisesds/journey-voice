## 2. Root cause of the 27 MB `mcp` bundle

`supabase/functions/mcp/index.ts` is 8.7 KB. The Lovable Vite plugin generates it from `src/lib/mcp/` (its banner says: AUTO-GENERATED, do not edit). It imports `npm:@lovable.dev/mcp-js@0.20.0`, `npm:@supabase/supabase-js@^2.99.3` and `npm:zod@^3.25.76`.

`npm view @lovable.dev/mcp-js@0.20.0` shows:
- dependencies: `jose ^6.2.2`, **`esbuild ^0.27.0`**, `@modelcontextprotocol/sdk 1.28.0`;
- peerDependencies: `zod >=3.23.0`, **`vite >=5.0.0 <9.0.0`**.

esbuild and vite are there for the package's Vite plugin, at BUILD time. The edge handler (`/stacks/supabase`) does not need them. Deno still resolves both into the function's npm graph, including their platform-native binaries.

`deno info --no-config index.ts` (deno 2.9.6, on a fresh cache):

| measurement | graph size | largest packages |
|---|---|---|
| as committed (the vite peer floats to **8.3.5**) | **94.12 MB**, 170 deps | `@rolldown/binding-linux-x64-{gnu,musl}` 19.5 MB each; `@esbuild/linux-x64@0.27.7` 10.9 MB; `lightningcss-linux-x64-{gnu,musl}` 9.8 MB each; then `@modelcontextprotocol/sdk` 4.2 MB, zod 3.5 MB, `@supabase/auth-js` 2.9 MB |
| vite peer held at 7.1.12 (an experiment, not a fix) | **53.82 MB**, 195 deps | two esbuild binaries (0.25.12: 9.9 MB, 0.27.7: 10.6 MB), rollup gnu+musl 2.1 MB each |

**The three candidate causes, each checked:**

| candidate | verdict | evidence |
|---|---|---|
| the 3× duplicate imports | **not a cause** | identical specifiers resolve to ONE module in Deno's graph. `deno info` lists `@lovable.dev/mcp-js@0.20.0` once. |
| the unpinned `^` ranges in index.ts | **minor** | supabase-js resolves to 2.118.0 (~7 MB across its packages), zod to 3.25.76. Pinning them saves little. |
| mcp-js's own dependency tree | **the cause** | about 60-80 MB of the graph is build-tool native binaries (rolldown, esbuild, lightningcss) that come in through mcp-js's `esbuild` dependency and its `vite` peer. The `<9.0.0` peer range lets vite float to 8, which brings rolldown and lightningcss. That probably explains why a 2026-07-09 deploy fit and today's does not (inference: the July bundle size was not recorded). |

**Why it is excluded rather than shrunk:** no edit to `index.ts` removes binaries that mcp-js itself declares, and the file is regenerated by the Lovable plugin, so a hand edit would be overwritten. Even with vite held at 7, the graph is still about 54 MB. **No safe in-repo shrink exists**, so `mcp` leaves all-mode with a printed reason. It can still be deployed by name (`function_name: mcp`). That dispatch will 413 today, which is honest and visible.

**Is `mcp` used?** It is an external MCP server (`.lovable/mcp/manifest.json` → `/functions/v1/mcp`, name `taskos-mcp`). No code in journey-voice or huddle-extension-app calls it (grep of both repos, read-only). `function_edge_logs` show **0 requests to `/functions/v1/mcp` in the last 24 h** (the log window is capped at 24 h). The live v168 is untouched by this change.

## 3. The fix (commit 1184f8d)

- **`scripts/deploy-all-functions.sh`** (new) makes one `supabase functions deploy <slug> --project-ref …` call per folder. The slug set is the same one the CLI's bulk deploy uses: `supabase/functions/*/index.ts` with slug `^[A-Za-z][A-Za-z0-9_-]*$`, so `_shared`, dot-dirs and folders with no `index.ts` are skipped. It deliberately runs WITHOUT `set -e`, so a failure is recorded and the loop carries on. The reason recorded is the last meaningful line of that call's output (e.g. the 413 text). At the end it prints a `deployed / FAILED / excluded` table to the log and to `$GITHUB_STEP_SUMMARY`, then exits 1 if anything failed. If it finds zero functions it exits 2, because an empty loop must not look like a clean deploy. An exclusion that names a non-existent folder prints a warning.
- **"Deploy all functions" step** now calls that script, with `DEPLOY_ALL_EXCLUDE` defaulting to `mcp: <reason>`. Each skipped function prints `::warning::SKIPPED mcp (excluded from all-mode): …` and gets its own `excluded` row. It is never silent.
- **Unchanged:** `mode=single`, `mode=list`, J12's blank-dispatch refusal (`deploy-dispatch-mode.test.mjs` D1–D3 still pass), the main-ancestry guard, and the secret sync. `check-edge-deploy-drift.yml` still runs on `workflow_run: completed` of this workflow. It fires whether the job ends green or red, and the job's name is unchanged.

## 4. Tests and mutations

`scripts/deploy-all-functions.test.mjs` takes the REAL step's `run:` block from the workflow file. It runs it under `bash -e`, as GitHub does, with a stub `supabase` first on PATH. The stub records every call and exits 1 with a 413 line for any slug in `STUB_FAIL`. 11 checks, all passing. `npm test`: 329 pass / 0 fail, and the new file is collected by `scripts/run-tests.mjs` under the `scripts` root.

| mutation (via `mutate.sh`, anchors from files) | check that must fail | outcome |
